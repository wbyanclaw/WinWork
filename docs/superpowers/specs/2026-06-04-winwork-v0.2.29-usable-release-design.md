# WinWork v0.2.29 可用版本 Spec

日期：2026-06-04
状态：Formal baseline approved 2026-06-04 by @yan
项目：winwork
版本目标：v0.2.29

## 1. 目标

v0.2.29 的目标不是继续修补 v0.2.28，而是交付一个“人类可以真正开始使用”的版本。

本版本只承诺三层能力：
- L0：B-scheme UI 骨架稳定
- L1：wind-cli 依赖入口可用
- L2：工作区最低可用交互成立

本版本**不承诺**知识库完整闭环；该部分进入 v0.3.0。

## 2. 为什么要单独做 v0.2.29

v0.2.28 的问题不是单点 bug，而是“页面骨架已接近正确，但产品可用性仍未闭环”。

当前明确阻塞包括：
1. 新用户首次安装 wind-cli 的主链路未闭合
2. 工作区只能列和读，缺搜索、缺真正预览
3. 知识库功能在 winwork 和 wind-cli 两边同时缺失
4. 同一版本同时承担“UI 纠偏 + 交互闭环 + 知识库闭环”风险过高

因此 v0.2.29 需要收敛为一个**可用版**，而不是一个“所有能力都试图碰一下”的版本。

## 3. v0.2.29 产品边界

### 3.1 必须交付

#### L0. B-scheme UI 骨架稳定
必须具备：
1. 顶栏 4 个状态胶囊
   - 就绪 / 未就绪
   - 当前模型
   - winwork 版本
   - wind-cli 版本
2. 左栏双 section
   - 工作区
   - 知识库
3. 左栏底部按钮
   - 新建文件
   - 新对话
4. 中间对话区
   - 支持 markdown 渲染
   - 工具结果以卡片/结构化结果进入对话流
5. 右侧详情滑出
   - 文件信息
   - 完整 trace
   - 溯源

L0 稳定的可测定义：
1. 首屏打开后，4 个胶囊必须在合理时间内填实，不能长期停留在 `…` 占位。
2. 切对话、切文件、切 tab 不得抛前端异常。
3. v0.2.27 中出现过的模板字面量转义错误、空元素引用错误不得再现。

#### L1. wind-cli 依赖入口可用
必须具备：
1. 首次启动可正确探测 wind-cli 是否存在
2. 未安装时可通过正式入口完成安装或升级引导
3. `trigger_install` 前后端链路完整存在
4. 安装/检查/升级结果回到 UI 是结构化状态，不靠字符串猜测
5. 顶栏 wind-cli 状态 pill 必须可点 → 触发升级 / 检查更新入口（v0.2.29.1 hotfix 补回，修复 v0.2.29 回归）

#### L2. 工作区最低可用交互
必须具备：
1. 查询
   - 文件树能稳定列出 workspace 与 wiki
   - 对话中可发起针对工作区的基本查询
   - UI 必须显式展示当前 workspace 路径，且允许用户切换（v0.2.29.1 hotfix 补回）
2. 预览
   - `.md` 不是纯文本生硬显示，而是 markdown 预览
   - 普通文本文件继续以可读文本显示
3. 搜索
   - 最低承诺为文件名 / 路径分段的模糊匹配与过滤
   - 结果能回到左栏或结果区域，并给出基本结果反馈
   - 不承诺内容 grep、glob pattern、metadata filter
4. 基本文件查看链路
   - 点击文件 -> 打开详情/预览
   - trace 可见本次读取行为
   - detail-trace header 必须显示最近一次 CLI 调用的命令/退出码/耗时（v0.2.29.1 hotfix 补回）
5. L2 chat 行为边界
   - 分两层：直接回答层（无需工具）/ 工作区写层（需触发工具）
   - 落盘需显式触发或显式默认，**不允许隐式写盘**（v0.2.29.1 hotfix 收口）
   - CLI 触发策略当前为 **temporary heuristic**（关键词收窄），v0.3.0 引入意图分类器

### 3.2 本版本明确不承诺

以下内容不属于 v0.2.29 的完成标准：
1. 知识库完整闭环
   - wiki ingest
   - wiki query
   - wiki build / reindex / precompile
2. llm-wiki-lib 独立能力在 winwork 侧完整呈现
3. “一键把当前文件入库并可立即检索”的完整工作流
4. 跨组件知识库依赖协调完成

这些统一进入 v0.3.0。

## 4. v0.2.29 的最低验收线

只有同时满足以下条件，v0.2.29 才算通过：

### 4.1 首次使用可启动
1. 新机器第一次打开应用
2. 能正确判断 wind-cli 是否存在
3. 若不存在，安装入口可用且不会因 invoke 未注册直接失败
4. 安装完成后状态能回到 UI

### 4.2 页面骨架与当前设计一致
1. 用户看到的首屏必须是 B-scheme
2. 不能再回退到旧版 `0.2.23` 风格页面
3. release 包与共享代码必须一致

### 4.3 工作区可用
1. 用户能看到文件树
2. 用户能打开文件
3. markdown 文件能被预览
4. 用户能搜索文件
5. 对话中的文件操作结果能体现在 UI

### 4.4 工程交付材料齐全
本版本发布时必须同时交付：
1. 开发规格书
2. 测试验收报告

没有测试验收报告，不允许宣称“版本可用”。

## 5. 关键设计决定

### 5.1 不把知识库链路继续塞进 v0.2.29
原因：
1. 缺口不只在 winwork
2. wind-cli 侧缺 wiki 子命令实现
3. winwork 单边无法闭环
4. 会拖垮版本可用性目标

### 5.2 先做 invoke 闭环审计，再做功能开发
v0.2.29 第一刀必须先做：
- 前端 `invoke(...)` 使用点清单
- Rust `generate_handler!` 注册清单
- 做差集，保证不存在“前端能调但后端没注册”的断链

这是 v0.2.29 的地基，不是可选优化。

### 5.3 预览优先于更复杂查询
本版本里，真正会直接影响“能不能用”的是：
- 能不能看到文件内容
- markdown 是否可读
- 能不能找到文件

所以优先顺序：
1. 预览
2. 搜索
3. 结构化查询增强

## 6. 版本拆分

### v0.2.29
范围：L0 + L1 + L2
目标：形成一个可真实开始使用的 winwork 基础版本

### v0.3.0
范围：L3 知识库完整闭环
目标：
- winwork 与 wind-cli 的 wiki 链路贯通
- 明确 build / ingest / query / reindex 的职责边界
- 配套知识库 UI 与测试验收报告

## 7. 测试验收要求

v0.2.29 的测试验收报告至少覆盖：
1. 新机器首次启动 / 安装 wind-cli
2. 页面骨架对齐
3. 文件树加载
4. 文件打开
5. markdown 预览
6. 文件搜索
7. 对话触发文件操作后的 UI 回流
8. release 包下载后实际运行结果

测试验收报告至少包含以下字段：
- 验收点
- 用例 ID
- 工程侧验证
- 用户侧实机验证
- 结论

要求同时包含：
- 工程侧验证
- 用户侧实机验证

## 8. 当前结论

v0.2.29 是“完整可用版”的第一阶段，不是终局版。

它的成功标准不是“知识库也差不多有了”，而是：
- 用户首次能进
- 页面不再回退
- 文件能看
- 文件能搜
- 工作区基本能用

只要这条线没过，就不应往 `done` 推。
